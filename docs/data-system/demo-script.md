# Guided capstone demo

Start the local server as described in the README, open http://localhost:8000,
and connect with the local token. Click **Run demo**. No uploads, typing, or
manual reviews are needed.

The backend performs the real operations first, then the browser presents their
captured results in six stages. Steps remain visible until you choose another:

1. **Ingest the PDF:** validates the bundled fictional PDF, stores its bytes,
   extracts pages, and creates searchable chunks. Shows actual extracted text.
2. **Store and read the assignment:** writes an example assignment, pins the PDF
   version, and reads it back from PostgreSQL in the same transaction.
3. **Retrieve evidence:** searches `timeline` in that source version with the
   existing access checks, returning the passage about six weeks and its page.
4. **Display the original source:** shows the stored PDF for comparison. This
   display does not claim that a human verified or approved the evidence.
5. **Calculate spending:** imports the five bundled CSV payments under a unique
   run key and calculates $280 consulting, $500 operational, $50 unresolved,
   and 2.80% of the matching $10,000 October budget, including the -$20 refund.
6. **Record a sample correction:** a clearly labeled scripted decision classifies
   the sample $50 as consulting, yielding $330 and 3.30%, with an actual audit entry.

Control the pace with **Next** and **Previous**, or click any stage directly.
There is no timer or autoplay setting. Each stage includes “What happens” and
“Tools & methods” summaries. Detailed speaking guidance remains below.
**Run demo again** executes a fresh run, always starting from the same fixture.
If an error appears, fix the connection and retry; no partial demo records persist.

## Isolation and limits

`POST /api/v1/demo/run` requires the local token, department access, and a reviewer
or administrator role. It uses the existing ingestion, assignment, retrieval,
import, spending, and correction services inside a rollback-only transaction.
Unique document IDs and import keys avoid touching existing user records. Even
on failure, temporary records roll back. Audit sequence numbers may advance,
but no demo audit rows remain. No AI model is called.

The UI displays captured results after execution, not a live progress stream.
The demo proves database writes/read-back inside a transaction; it does not claim
those temporary records survive a reload. Use the manual workspace below to
show permanent assignments, uploads, and corrections. Report storage/reviews,
recovery, and production integration are outside the automatic walkthrough.

## Verification

Run `.venv/bin/python scripts/validate_data.py --disposable --browser`.
Backend coverage checks repeatability, access rejection, and preservation of a
previously corrected payment and all affected table counts. Browser coverage
checks manual stepping, staying on the same step after time passes, replay, source
display, and API failure.
Local logs and screenshots are saved under `evidence/local/`.

## How to explain the complete process

Opening: “My subsystem is the data and knowledge layer. It converts documents
and payments into structured, searchable, traceable records for the consulting
engine. Run demo executes the actual backend workflow once. I use Next to explain
its captured results at my own pace. It uses fictional data and rolls back its
temporary records afterward, so I can repeat it without changing saved work.”

### 1. Ingest the PDF

Say: “First, I turn a document into usable evidence. The backend checks the PDF,
keeps the original file and a fingerprint of its contents, and extracts text from
each page. It divides the text into smaller passages called chunks. Each chunk
keeps its document version and page number. Ready means extraction completed;
the text you see was read from the file, not generated by an AI.”

Point to the ready status, actual chunk count, and page labels. Chunks are limited
to 1,200 characters and never cross pages. A content hash fingerprints the bytes;
it does not prove the document's claims are true. Unreadable or image-only pages
produce an extraction failure; OCR is not implemented.

Transition: “Now that the source is usable, I connect it to a consulting task.”

### 2. Store and read the assignment

Say: “The task is to improve permit intake. I store that problem, the intended
result, and the selected source version in PostgreSQL. The backend checks access,
creates an assignment ID, and reads the saved row back. Pinning a version means
a future upload does not silently replace the evidence for this assignment.”

Point to the problem, intended result, selected-version count, and assignment ID.
This is a real database write and read within the demo transaction. It does not
prove persistence after rollback. Permanent save/reload behavior is available in
the manual workspace and covered by browser tests.

Transition: “Instead of handing every document to the engine, I retrieve the
passages relevant to the question.”

### 3. Retrieve evidence

Say: “Here I search for timeline. PostgreSQL performs full-text keyword matching,
filters out sources the user cannot access, and limits results to the selected
version. It ranks matches and returns the source text with its title and page.
The six-week timeline comes from that passage; the system did not invent it.”

Point to the query, passage, and page locator. The search checks department access,
ready status, unknown access, document restrictions, and the selected version.
This local run does not request external-model use. Search is keyword-based, not
vector search, and does not produce a recommendation. No matches produce an
evidence gap rather than a fabricated answer.

Transition: “A result is useful only if we can trace it back to its source.”

### 4. Display the original source

Say: “The backend rechecks access and retrieves the original PDF bytes for this
version. Page 1 contains the same six-week passage. That lets someone inspect the
original context instead of trusting a detached excerpt.”

Point to page 1; use the new-tab link if the embedded PDF is too small. Displaying
the PDF establishes traceability. It does not certify the source's accuracy or
record a human approval. This guided demo requires no manual review submission.

Transition: “The same subsystem also turns payment records into explainable totals.”

### 5. Calculate spending

Say: “The backend imports five fictional payment rows from a CSV. It validates
fields, matches vendor and department identities, and calculates totals for the
specified October source population. Consulting is 100 plus 200 minus a 20-dollar
refund, which equals 280 dollars. Operational spending is 500, and 50 remains
unresolved. Consulting is 2.80 percent of the matching 10,000-dollar budget.”

Point to each category. Money uses decimal arithmetic. The full payment total is
$830. The $10,000 denominator is a budget, not the sum of the imported payments.
Unresolved spending stays separate because its category is not established.
The unique demo import key prevents these rows from updating existing payments.

Transition: “When a category needs correcting, the system must preserve why it changed.”

### 6. Record a sample correction

Say: “For demonstration, a scripted decision classifies the unresolved 50 dollars
as consulting. The correction service checks reviewer permission and verifies
that the payment still has the expected old classification. It records the old
and new categories, actor, reason, and time, then recalculates spending. Consulting
becomes 330, unresolved becomes zero, and the budget share becomes 3.30 percent.”

Point to the before/after amounts and audit record. Operational spending remains
$500 and the overall total remains $830: no new money was added. The expected-old-
category check rejects stale edits. The classification is a scripted example,
not a judgment inferred from the PDF. A real correction needs a justified human
decision. Demo audit rows roll back with the rest of the run; normal corrections
in the manual workspace persist.

Closing: “The subsystem provides usable evidence, source traceability, accurate
spending calculations, and accountable corrections. These are inputs the engine
can build on. This walkthrough does not call an AI model, generate a report, or
claim that the full team's production application is complete.”
